## Часть 2. Исправление дефекта (папка `brownfield`)

Основной текст — баг-репорт без готового решения: [bug-reconnect.md](bug-reconnect.md). Ниже вариант с репетиции, где причина названа прямо; он запасной.

```
/opsx:ff fix-reconnect-backoff: стенд сравнения (benchmarks/Redis.Client.Comparison, `dotnet run -c Release -- chaos --only down`) показал, что после 10 с недоступности Redis наш клиент восстанавливается за 7,8 с, а StackExchange.Redis за 2,1 с. Причина — экспоненциальная пауза между попытками переподключения растёт до ReconnectMaxDelay = 30 с, и клиент «спит», когда сервер уже вернулся. Нужно, чтобы клиент переподключался быстро после возвращения сервера, но не заваливал сервер попытками во время простоя. Зафиксируй решение в design, измени требования в spec и добавь тест, который проверяет скорость восстановления.
```

### Ревью design

Haiku каждый раз предлагает разное. На репетициях было два неудачных варианта: «сбрасывать счётчик попыток после подключения» (он и так сбрасывается) и «базовая пауза 10 мс, рост не больше 320 мс» (клиент стучится в сервер трижды в секунду). На любой неудачный вариант — эта реплика. Она не называет ответ, а задаёт проверочные вопросы по требованиям из бага. Проверено на втором варианте: Haiku сам пришёл к `ReconnectMaxDelay` 1,5 с.

```
Решение не подходит. Проверь его по требованиям из бага:
1. Время восстановления после возвращения сервера ограничено сверху самой длинной паузой между попытками. Какой она должна быть, чтобы уложиться в 2 с?
2. Сколько попыток в секунду клиент делает, если сервер недоступен несколько минут? Требование — не заваливать сервер.
3. Не дублирует ли решение то, что уже есть: счётчик попыток обнуляется после успешного подключения (src/Redis.Client/Connections/MultiplexedConnection.cs, `attempt = 0`).
Пересмотри design и spec, обнови tasks.
```

Если design сразу верный («`ReconnectMaxDelay` по умолчанию 30 с → 2 с, рост и jitter сохраняются»), ревью всё равно есть что сказать — это то, что сломалось на первой репетиции:

```
Решение принимаю, два замечания:
1. Старое значение 30 с осталось в таблице значений по умолчанию в openspec/specs/client-configuration/spec.md и в README.md — их тоже нужно обновить.
2. Тест на скорость восстановления: считай время от момента, когда сервер снова доступен, а не от начала простоя. И не держи одну команду в очереди весь простой — она истечёт по CommandTimeout (5 с) раньше, чем сервер вернётся.
```

```
/opsx:apply
```

Если после apply задачи отмечены, а тесты не запускались, это реплика проверки:

```
Прогони модульные тесты и свой новый интеграционный тест. Сверь отметки в tasks.md с реальными изменениями в коде и сними отметки с того, что не сделано. Проверь README и openspec/specs на упоминания старого значения 30 с.
```
