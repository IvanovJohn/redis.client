## ADDED Requirements

### Requirement: Сериализация команд
Клиент SHALL кодировать каждую команду как RESP-массив bulk strings. Имя команды и аргументы MUST передаваться бинарно-безопасно: произвольные байты, включая `\r\n` и `\0`, отправляются без искажений.

#### Scenario: Команда со строковыми аргументами
- **WHEN** клиент отправляет `SET key value`
- **THEN** в сокет записываются байты `*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n`

#### Scenario: Бинарное значение
- **WHEN** клиент отправляет `SET` со значением, содержащим байты `0x00 0x0D 0x0A 0xFF`
- **THEN** последующий `GET` возвращает ровно эти четыре байта

#### Scenario: Строка в UTF-8
- **WHEN** аргумент передан как `string` с не-ASCII символами (например, `"ключ"`)
- **THEN** он кодируется в UTF-8, а длина в заголовке bulk string равна числу байт, а не символов

### Requirement: Разбор типов RESP2
Парсер SHALL поддерживать все типы RESP2: simple string (`+`), error (`-`), integer (`:`), bulk string (`$`), включая null bulk string (`$-1`), и array (`*`), включая null array (`*-1`) и вложенные массивы.

#### Scenario: Null bulk string
- **WHEN** сервер отвечает `$-1\r\n`
- **THEN** парсер возвращает кадр типа Null

#### Scenario: Вложенный массив
- **WHEN** сервер отвечает `*2\r\n*1\r\n:1\r\n$1\r\na\r\n`
- **THEN** парсер возвращает массив из двух элементов: массива с целым `1` и bulk string `a`

### Requirement: Разбор типов RESP3
Парсер SHALL поддерживать все типы RESP3:
- null (`_`);
- boolean (`#`);
- double (`,`), включая `inf`, `-inf` и `nan`;
- big number (`(`);
- bulk error (`!`);
- verbatim string (`=`);
- map (`%`), set (`~`), push (`>`);
- attribute (`|`).

#### Scenario: Map
- **WHEN** сервер отвечает `%1\r\n+field\r\n:42\r\n`
- **THEN** парсер возвращает map с одной парой `field → 42`

#### Scenario: Специальные значения double
- **WHEN** сервер отвечает `,inf\r\n`
- **THEN** результат равен `double.PositiveInfinity`

#### Scenario: Verbatim string
- **WHEN** сервер отвечает `=15\r\ntxt:Some string\r\n`
- **THEN** результат — строка `Some string` с форматом `txt`

#### Scenario: Атрибут перед ответом
- **WHEN** перед ответом пришёл кадр атрибутов `|`
- **THEN** атрибуты не считаются отдельным ответом, и ожидающая команда получает следующий за ними кадр

### Requirement: Инкрементальный разбор
Парсер MUST корректно обрабатывать кадры, пришедшие по частям через несколько чтений из сети, в том числе с разрывом внутри заголовка, внутри тела или между `\r` и `\n`.

#### Scenario: Ответ пришёл побайтно
- **WHEN** ответ `$5\r\nhello\r\n` поступает в парсер по одному байту
- **THEN** парсер сообщает о неполном кадре до последнего байта, а затем возвращает bulk string `hello`

#### Scenario: Несколько ответов в одном чтении
- **WHEN** одно чтение из сети содержит три полных ответа и начало четвёртого
- **THEN** парсер возвращает три кадра и ждёт данных для четвёртого, не теряя уже прочитанные байты

### Requirement: Ограничения на размер и вложенность
Парсер SHALL ограничивать длину bulk string и число элементов агрегата значением `MaxBulkLength`, а глубину вложенности — значением `MaxNestingDepth`. Превышение ограничения MUST приводить к `RedisProtocolException` до выделения памяти под значение.

#### Scenario: Слишком длинный bulk string
- **WHEN** сервер присылает заголовок `$` с длиной больше `MaxBulkLength`
- **THEN** парсер выбрасывает `RedisProtocolException` и не аллоцирует буфер заявленного размера

#### Scenario: Слишком глубокая вложенность
- **WHEN** глубина вложенности массивов превышает `MaxNestingDepth`
- **THEN** парсер выбрасывает `RedisProtocolException`

### Requirement: Некорректный поток данных
При синтаксически некорректных данных (неизвестный тип кадра, нечисловая длина, отсутствие `\r\n`) парсер SHALL выбрасывать `RedisProtocolException`. Соединение MUST быть разорвано: после ошибки протокола соответствие запросов и ответов не гарантировано.

#### Scenario: Неизвестный байт типа
- **WHEN** кадр начинается с байта `@`
- **THEN** выбрасывается `RedisProtocolException`, соединение закрывается, и все ожидающие на нём команды завершаются ошибкой

### Requirement: Ошибки сервера
Ответы-ошибки (`-` и `!`) SHALL превращаться в `RedisServerException`. Исключение MUST содержать код ошибки (первое слово сообщения, например `WRONGTYPE`, `NOAUTH`, `NOSCRIPT`) и полный текст. Ошибка сервера MUST NOT разрывать соединение.

#### Scenario: Операция над ключом другого типа
- **WHEN** клиент выполняет `LPUSH` над ключом, содержащим строку
- **THEN** вызов завершается `RedisServerException` с кодом `WRONGTYPE`, а следующая команда на том же соединении выполняется успешно

### Requirement: Согласование версии протокола
При установке соединения клиент SHALL отправлять `HELLO 3`. Если сервер ответил ошибкой на `HELLO`, клиент MUST продолжить на RESP2. Опция `Protocol` SHALL позволять зафиксировать RESP2 или RESP3 явно. При явно заданном RESP3 ошибка `HELLO` MUST приводить к ошибке подключения, а не к откату.

#### Scenario: Сервер поддерживает RESP3
- **WHEN** клиент подключается к Redis 7.x с настройками по умолчанию
- **THEN** соединение работает по RESP3

#### Scenario: Прокси не поддерживает HELLO
- **WHEN** на `HELLO 3` пришла ошибка `ERR unknown command`
- **THEN** клиент продолжает handshake по RESP2 (`AUTH`, `CLIENT SETNAME`), и соединение становится рабочим

#### Scenario: Явно задан RESP2
- **WHEN** `Protocol = Resp2`
- **THEN** клиент не отправляет `HELLO 3` и работает по RESP2

### Requirement: Push-сообщения RESP3
Кадры типа push (`>`) SHALL NOT сопоставляться с ожидающими командами. Они MUST передаваться в отдельный обработчик push-сообщений соединения.

#### Scenario: Push между ответами
- **WHEN** между ответами на две команды сервер прислал push-кадр
- **THEN** обе команды получают свои ответы, а push-кадр уходит в обработчик push-сообщений
