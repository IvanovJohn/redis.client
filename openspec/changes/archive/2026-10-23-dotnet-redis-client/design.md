## Context

Проект пустой: кода и существующих spec нет. Мотивация и границы описаны в `proposal.md`. Нужно написать с нуля Redis-клиент для .NET 10, который будет работать в enterprise-сервисах. Это значит:

- высокая конкурентность: тысячи одновременных async-вызовов из одного процесса;
- сеть ненадёжна: бывают разрывы, failover, перезапуски Redis;
- требования безопасности: TLS, ACL, ротация секретов, никаких секретов и данных в логах;
- эксплуатация через OpenTelemetry и DI-контейнер;
- Cluster и Sentinel в этот change не входят, но придут следующими. Архитектура не должна их блокировать.

## Goals / Non-Goals

**Goals:**
- Корректная реализация RESP2/RESP3 без аллокаций на горячем пути, где это достижимо.
- Мультиплексированное соединение с естественным pipelining: пропускная способность близка к StackExchange.Redis.
- Предсказуемое поведение при сбоях: явные таймауты, явные исключения, без скрытых повторов неидемпотентных команд.
- Мокаемый публичный API на интерфейсах; совместимость с NativeAOT и trimming (без reflection).
- Полная наблюдаемость через стандартные .NET API (`ILogger`, `Meter`, `ActivitySource`).
- Точки расширения под будущую маршрутизацию Cluster/Sentinel.

**Non-Goals:**
- Cluster, Sentinel, client-side caching, синхронный API (см. proposal).
- Сериализация объектов (JSON, MessagePack): клиент работает с байтами, строками и числами. Сериализацию добавляет пользователь сверху.
- Поддержка Redis ниже 6.2. Минимальная версия 6.2 даёт `HELLO`/ACL, `GETDEL`, `GETEX`, `LMOVE`/`BLMOVE`, `SMISMEMBER` и единый `ZRANGE ... BYSCORE|BYLEX|REV|LIMIT`, поэтому в API не нужны обходные пути для старых серверов.
- Совместимость с Redis-совместимыми серверами (Valkey, Dragonfly, KeyDB). Поддерживается и тестируется только Redis.

## Decisions

### D1. Транспорт: `Socket` + `SslStream` + `System.IO.Pipelines`

Чтение и запись идут через `PipeReader`/`PipeWriter` поверх сокета, а при TLS поверх `SslStream`.

- **Почему:** пулинг буферов, встроенный backpressure и работа с `ReadOnlySequence<byte>` позволяют парсить ответы, которые пришли частями, без копирования.
- **Альтернативы:**
  - `NetworkStream` с собственными буферами: больше ручного кода и больше ошибок на границах буферов;
  - `SocketAsyncEventArgs`: максимальный контроль, но сложнее и не даёт выигрыша, который бы это оправдал.

### D2. Модель конкурентности: мультиплексор с FIFO-очередью ожиданий

Одно физическое соединение обслуживает всех вызывающих.

- **Запись:** команды попадают в `Channel<PendingCommand>`. Единственный writer-loop вычитывает из канала всё, что накопилось, сериализует пачкой в `PipeWriter` и делает один `FlushAsync`. Так получается автоматический pipelining и coalescing.
- **Ожидания:** каждая записанная команда попадает в FIFO-очередь ожиданий со своим `TaskCompletionSource`.
- **Чтение:** единственный reader-loop парсит ответы и завершает ожидания строго по порядку. RESP3 push-сообщения не попадают в FIFO и маршрутизируются отдельно.
- **Число соединений:** опция `MultiplexedConnectionCount` (по умолчанию 1) задаёт N мультиплексированных соединений с round-robin. Это смягчает head-of-line blocking на больших значениях.
- **Альтернатива:** пул соединений «одна команда на соединение» (как в Npgsql). Её отвергли: нужно на порядки больше соединений к Redis, и pipelining теряется.

### D3. Выделенные соединения для блокирующих и stateful-операций

Некоторые команды нельзя выполнять на общем соединении, потому что они либо блокируют его, либо держат состояние на уровне соединения:

- блокирующие команды: `BLPOP`, `BRPOP`, `BLMOVE`, `BZPOPMIN`/`BZPOPMAX`, `WAIT`;
- транзакции с `WATCH`.

Такие операции арендуют соединение из ограниченного пула (`DedicatedPoolSize`). Каждое соединение пула проходит тот же handshake. Если пул исчерпан, вызов ждёт свободное соединение до таймаута.

Дедлайн блокирующей команды на клиенте равен её серверному таймауту плюс `CommandTimeout`. Так легитимное ожидание не обрывается клиентским таймаутом.

Метаданные команды содержат флаг `Blocking`. По нему пользователь не может случайно отправить блокирующую команду в мультиплексор, в том числе через `ExecuteAsync`.

### D4. Парсер RESP: инкрементальный, поверх `SequenceReader<byte>`

- **Возобновление:** разбор идёт в два шага.
  - Возобновляемый сканер (`RespScanner`) с явным стеком проверяет, что кадр полный и корректный. Если данных не хватает, он запоминает уже проверенную часть, и после следующего чтения продолжает с этого места. Позиция в pipe не сдвигается до полного кадра. Так ответ из миллиона элементов, пришедший тысячами чтений, проверяется за линейное время. Изначально планировался повторный разбор с начала кадра, но он квадратичен на больших ответах.
  - Уже проверенный кадр читается без проверок через `RespFrame`.
- **Вложенность:** агрегаты (array, map, set, push, attribute) разбираются с ограничением глубины (`MaxNestingDepth`).
- **Защита от OOM:** размер bulk string и агрегатов ограничен (`MaxBulkLength`, по умолчанию 512 МБ, как лимит Redis). Повреждённый поток ведёт к разрыву соединения, а не к попытке аллоцировать гигабайты.
- **Результат разбора:** легковесная структура `RespFrame` с типом и срезом буфера. Типизированное преобразование (`long`, `string`, `byte[]`, массивы) делают result-парсеры команд, и данные копируются только там.
- **Атрибуты RESP3:** атрибуты (`|`) пропускаются, но доступны через низкоуровневый API.

### D5. Протокол: RESP3 по умолчанию с откатом на RESP2

- **Handshake:** `HELLO 3 [AUTH user pass] [SETNAME name]`, затем `SELECT db`, если база не 0.
- **Откат:** Redis 6.2+ всегда поддерживает `HELLO`, но прокси и managed-сервисы перед ним (Envoy, twemproxy, часть облачных предложений) могут его не пропускать. Поэтому, если `HELLO` вернул ошибку, используется RESP2 с отдельными `AUTH`/`CLIENT SETNAME`. Опция `Protocol` позволяет зафиксировать версию явно.
- **Версия сервера:** берётся из ответа `HELLO` (или из `INFO server` на RESP2), пишется в лог и в атрибуты трассировки. Клиент сам не проверяет, поддерживает ли сервер команду: команды новее 6.2 (например, `EVAL_RO`, `LMPOP` из 7.0) отправляются как есть, а в XML-документации у них указана минимальная версия. На старом сервере такая команда падает с `RedisServerException` (`ERR unknown command`).
- **Почему RESP3:** типизированные ответы (map, double, boolean) и push-сообщения.
- **Совместимость API:** result-парсеры команд нормализуют различия протоколов. Например, `HGETALL` возвращает map в RESP3 и плоский массив в RESP2, а пользователь видит один и тот же результат.

### D6. Pub/Sub на отдельном соединении, независимо от протокола

Для подписок лениво создаётся одно выделенное соединение.

- **Альтернатива:** в RESP3 подписки можно держать на общем мультиплексированном соединении. Это отвергли ради единообразия с RESP2 и изоляции: поток сообщений не должен задерживать ответы на команды.
- **Восстановление:** клиент хранит реестр подписок (каналы, паттерны, обработчики) и после переподключения переподписывается автоматически.
- **Доставка:** обработчики вызываются через ограниченный `Channel` на каждую подписку, чтобы медленный потребитель не блокировал reader-loop.
- **Медленный потребитель:** политика переполнения настраивается (`DropOldest` или `Wait`), а потери сообщений учитываются в метриках.
- **API:** `IAsyncEnumerable<RedisMessage>` и callback-вариант.

### D7. Транзакции

- **Без `WATCH`.** `MULTI`, команды и `EXEC` буферизуются на клиенте и уходят в мультиплексор одним непрерывным блоком: writer-loop гарантирует, что чужие команды не вклинятся. Результаты всех команд транзакции разбираются из ответа `EXEC`.
- **С `WATCH`.** Используется выделенное соединение (D3), потому что `WATCH` действует на уровне соединения, и чужой `EXEC` на общем соединении сбросил бы наблюдение. API выглядит так: `await using var tx = await client.BeginWatchedTransactionAsync(keys, ct)`. Пользователь читает значения через `tx`, затем вызывает `ExecuteAsync`, который возвращает `null`/`false` при конфликте.
- **Альтернатива:** «условия» в стиле StackExchange.Redis, которые проверяются внутри транзакции. Её отвергли: модель сложнее для понимания, а для оптимистичных блокировок выделенное соединение проще и прозрачнее.

### D8. Скрипты: `LuaScript` с кэшем SHA1

Объект скрипта считает SHA1 при создании. Вызов выполняет `EVALSHA`, а на ошибку `NOSCRIPT` прозрачно отвечает `EVAL`, после которого скрипт закэширован на сервере. Отдельный `ScriptLoadAsync` позволяет прогреть кэш заранее. `EVAL_RO`/`EVALSHA_RO` поддерживаются флагом. Они требуют Redis 7.0+ (см. D5 о командах новее минимальной версии).

### D9. Публичный API

Точка входа — интерфейс `IRedisClient`. Он `IAsyncDisposable`, потокобезопасен и рассчитан на один экземпляр на приложение. Команды сгруппированы в интерфейсы-свойства: `client.Keys`, `client.Strings`, `client.Hashes`, `client.Lists`, `client.Sets`, `client.SortedSets`. Рядом с ними `client.ExecuteAsync(...)` для произвольных команд, `client.Subscriber`, транзакции и скрипты.

- **Почему группы-интерфейсы:** каждую группу можно замокать отдельно, а IntelliSense не превращается в список из 300 методов. Отвергнутые альтернативы:
  - один гигантский интерфейс в стиле `IDatabase`: неудобен для моков и навигации;
  - extension-методы поверх `ExecuteAsync`: их невозможно замокать.
- **Значения:** `RedisKey` и `RedisValue` — readonly structs с неявными преобразованиями из `string` (UTF-8), `byte[]`, `ReadOnlyMemory<byte>`, `long` и `double`. Это избавляет от взрыва перегрузок. Отсутствующее значение (`nil`) представлено как `RedisValue.Null`, а не как исключение.
- **Async:** все методы возвращают `ValueTask`/`ValueTask<T>` и принимают `CancellationToken`.
- **Ошибки:** иерархия исключений:
  - `RedisException` — базовый тип;
  - `RedisServerException` с кодом ошибки сервера (`WRONGTYPE`, `NOAUTH`, ...);
  - `RedisConnectionException`;
  - `RedisTimeoutException` с признаком «команда могла выполниться».

### D10. Сбои, переподключение, таймауты

**Таймауты и отмена.** У каждой команды есть дедлайн (`CommandTimeout`, можно переопределить на вызов) плюс `CancellationToken`. Поведение зависит от того, успела ли команда уйти в сеть:

- команда ещё не записана: она удаляется из очереди и гарантированно не выполнится;
- команда уже записана: ожидание завершается исключением, а слот в FIFO помечается как abandoned, и пришедший позже ответ отбрасывается. Синхронизация FIFO с потоком ответов не нарушается.

**Разрыв соединения.**
- Все записанные, но не отвеченные команды завершаются `RedisConnectionException`. Клиент не знает, выполнила ли их сервер, поэтому **автоповтора нет**.
- Незаписанные команды (backlog) обрабатываются по опции `BacklogPolicy`: `Queue` ждёт переподключения в пределах своего таймаута (поведение по умолчанию), `FailFast` падает сразу.
- Переподключение идёт с экспоненциальным backoff и jitter (`ReconnectBaseDelay`, `ReconnectMaxDelay`). После него повторяется handshake (D5) и восстанавливаются подписки (D6).
- Здоровье соединения проверяет контрольный `PING`, а также TCP keepalive. `PING` отправляется в двух случаях:
  - простой: с соединения ничего не читалось в течение `KeepAliveInterval`;
  - зависание: есть команды, ждущие ответа, а с соединения ничего не читалось 2×`CommandTimeout`.

  Без проверки на зависание «полуоткрытое» соединение (пир исчез за прокси или NAT, запись проходит, ответов нет) обнаруживалось бы только через `KeepAliveInterval`, а всё это время каждая команда падала бы по таймауту. Это показал soak-тест с перезапусками Redis за docker-proxy.

  Если `PING` не получил ответа за `CommandTimeout`, соединение пересоздаётся. Компромисс: серверная команда, молчащая дольше 3×`CommandTimeout`, тоже приводит к переподключению. Её вызывающий к этому моменту уже получил таймаут.

**Повторы.** Ретраи бизнес-операций остаются за пользователем (Polly/`Microsoft.Extensions.Resilience`), потому что идемпотентность знает только он. Клиент повторяет только handshake и подключение.

### D11. Конфигурация и DI

- **Options:** `RedisClientOptions` с валидацией через `IValidateOptions<T>`.
- **Endpoint'ы:** хранятся списком, хотя в этом change используется один. Это заготовка под Sentinel/Cluster, чтобы не ломать формат конфигурации позже.
- **Строка подключения:** стандартные URI `redis://user:pass@host:port/db` и `rediss://...` (TLS) с query-параметрами для остальных опций.
- **Секреты:** опция `CredentialsProvider` (`Func<CancellationToken, ValueTask<RedisCredentials>>`) вызывается при каждом подключении. Так поддерживается ротация паролей из Vault/Key Vault без перезапуска.
- **TLS:** настраивается через `SslClientAuthenticationOptions`: валидация сертификата, клиентские сертификаты, SNI.
- **DI:** `services.AddRedisClient(...)` регистрирует singleton. Именованные клиенты регистрируются через keyed services (`AddKeyedRedisClient("cache", ...)`), а `IOptionsMonitor` даёт привязку к `IConfiguration`.

### D12. Наблюдаемость

**Трассировка.** `ActivitySource` с именем `Redis.Client` по семантическим конвенциям OpenTelemetry для баз данных:

- атрибуты: `db.system.name=redis`, `db.operation.name`, `db.namespace`, `server.address`, `server.port`;
- текст команды с аргументами **не** записывается по умолчанию, потому что в аргументах могут быть персональные данные и секреты;
- опция `RecordCommandArguments` включает запись аргументов для отладки, при этом `AUTH`/`HELLO` всё равно маскируются.

**Метрики.** `Meter` с именем `Redis.Client`:

- `db.client.operation.duration` — гистограмма с тегами операции и результата;
- число активных соединений и переподключений;
- длина backlog и FIFO;
- таймауты;
- потерянные pub/sub-сообщения.

**Логи.** Source-generated `LoggerMessage`, без значений ключей и аргументов. На уровне `Information` пишутся события жизненного цикла соединения, `Debug` предназначен для диагностики.

### D13. Готовность к Cluster/Sentinel

**Маршрутизация.** Внутренний слой `ICommandRouter` выбирает соединение для команды. В этом change есть одна реализация — `SingleNodeRouter`.

**Метаданные команд.** Каждая команда несёт:
- позиции ключей, нужные для будущего вычисления hash slot;
- флаги `ReadOnly`, `Blocking` и `NoKey`.

Cluster потом добавит свой роутер и обработку `MOVED`/`ASK`, а публичный API менять не придётся.

### D14. Структура решения и качество

- **Проекты:**
  - `src/<Package>` — сама библиотека;
  - `tests/<Package>.Tests` — unit-тесты парсера и протокола, включая property-based и fuzz-тесты для RESP;
  - `tests/<Package>.IntegrationTests` — интеграционные тесты на Testcontainers: Redis 6.2 и 7.x, а также конфигурации с TLS и ACL;
  - `benchmarks/` — BenchmarkDotNet.
- **Сборка:**
  - `Nullable` включён, `TreatWarningsAsErrors` тоже;
  - `IsAotCompatible=true`, анализаторы trimming и AOT включены;
  - `Microsoft.CodeAnalysis.PublicApiAnalyzers` фиксирует публичный контракт.

## Risks / Trade-offs

- **[Ошибки в протоколе ломают синхронизацию FIFO, и ответы уходят «не тем» вызывающим].** Это самый опасный класс багов. Меры:
  - любая ошибка парсинга или нарушение инвариантов ведёт к немедленному разрыву соединения со сбросом всех ожиданий;
  - fuzz-тесты парсера;
  - интеграционные тесты под конкурентной нагрузкой со сверкой «запрос ↔ ответ».
- **[Head-of-line blocking: большое значение или медленная команда задерживает всех на мультиплексированном соединении].** Меры:
  - `MultiplexedConnectionCount > 1`;
  - метрики длины очереди;
  - документация рекомендует не хранить многомегабайтные значения и не использовать `KEYS`/`SMEMBERS` на больших множествах. Для обхода есть `SCAN`/`HSCAN`/`SSCAN`/`ZSCAN` через `IAsyncEnumerable`.
- **[Таймаут не означает, что команда не выполнилась].** Неоднозначность фундаментальна для любого сетевого клиента. Меры: признак `MayHaveExecuted` в исключении и явная документация; клиент не делает автоповторов.
- **[Сложность и стоимость поддержки собственного клиента по сравнению со StackExchange.Redis].** Это осознанный выбор (решение «с нуля» принято в proposal). Меры: строгий охват тестами, бенчмарки против StackExchange.Redis как ориентир и узкий поддерживаемый объём команд с `ExecuteAsync` как запасным выходом.
- **[Пул выделенных соединений исчерпан блокирующими командами].** Меры: ограниченный размер пула, таймаут ожидания аренды, метрики занятости и предупреждение в логах.
- **[Утечка секретов через логи и трассировку].** Меры: аргументы по умолчанию не пишутся, `AUTH`/`HELLO` маскируются всегда, отдельный тест проверяет, что пароль не попадает ни в один sink.

## Migration Plan

Миграции нет: это новая библиотека.

- **Версии:** `0.x` prerelease, пока API не стабилизируется. `1.0` выходит после прохождения нагрузочных тестов и ревью публичного API. С `1.0` действует SemVer, а изменения контракта контролирует PublicApiAnalyzers.
- **Откат:** откат для потребителей — пин на предыдущую версию пакета.
