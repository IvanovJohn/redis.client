## ADDED Requirements

### Requirement: Транзакция без WATCH
Клиент SHALL предоставлять `CreateTransaction()`. Команды транзакции MUST накапливаться на клиенте, а при вызове `ExecuteAsync` отправляться одним непрерывным блоком `MULTI … EXEC` через мультиплексированное соединение. Команды других вызывающих MUST NOT попадать между `MULTI` и `EXEC`. Каждая команда транзакции SHALL возвращать собственную задачу результата, которая завершается после `EXEC`.

#### Scenario: Успешная транзакция
- **WHEN** в транзакцию добавлены `INCR a` и `INCR b`, и вызван `ExecuteAsync`
- **THEN** обе задачи результатов завершаются значениями после `EXEC`, и на сервере выполнены обе команды

#### Scenario: Атомарность при конкурентной нагрузке
- **WHEN** 100 задач конкурентно выполняют транзакции `INCR counter; GET counter`, а другие задачи параллельно выполняют одиночные команды на том же соединении
- **THEN** в каждой транзакции значение `GET` равно результату её `INCR`

#### Scenario: Ошибка постановки в очередь
- **WHEN** одна из команд транзакции синтаксически некорректна, и сервер отвечает `EXECABORT`
- **THEN** `ExecuteAsync` завершается `RedisServerException` с кодом `EXECABORT`, все задачи результатов завершаются той же ошибкой, и ни одна команда не выполнена

#### Scenario: Ошибка выполнения одной команды
- **WHEN** в транзакции `SET k v; LPUSH k x` вторая команда падает с `WRONGTYPE`
- **THEN** задача результата `SET` завершается успешно, а задача `LPUSH` — `RedisServerException` с кодом `WRONGTYPE`, как того требует семантика Redis

#### Scenario: Транзакция не выполнена
- **WHEN** транзакция создана, в неё добавлены команды, но `ExecuteAsync` не вызван
- **THEN** на сервер ничего не отправляется

### Requirement: Транзакция с WATCH
Клиент SHALL предоставлять `BeginWatchedTransactionAsync(keys, ct)`. Метод арендует выделенное соединение и выполняет на нём `WATCH`. Объект транзакции MUST позволять:
- читать значения на том же соединении;
- накапливать команды;
- вызывать `ExecuteAsync`, который возвращает `true` при успехе и `false` при конфликте (`EXEC` вернул null).

При освобождении объекта соединение MUST возвращаться в пул в чистом состоянии (`UNWATCH`/`DISCARD` при необходимости).

#### Scenario: Оптимистичная блокировка без конфликта
- **WHEN** транзакция наблюдает ключ `balance`, читает его, ставит в очередь `SET balance <новое>` и выполняется, пока другие клиенты не меняли `balance`
- **THEN** `ExecuteAsync` возвращает `true`, и значение обновлено

#### Scenario: Конфликт
- **WHEN** после `WATCH balance` другой клиент изменил `balance` до вызова `ExecuteAsync`
- **THEN** `ExecuteAsync` возвращает `false`, команды транзакции не выполнены, а задачи их результатов завершаются отменой

#### Scenario: Возврат соединения в пул
- **WHEN** объект транзакции освобождён без вызова `ExecuteAsync`
- **THEN** соединение возвращается в пул, и следующая аренда не наблюдает ключи предыдущей транзакции

### Requirement: Выполнение Lua-скриптов
Клиент SHALL предоставлять тип `LuaScript` с текстом скрипта и предвычисленным SHA1. Выполнение скрипта MUST идти через `EVALSHA`. При ответе `NOSCRIPT` клиент MUST повторить вызов через `EVAL` в рамках того же вызова пользователя. Ключи и аргументы SHALL передаваться раздельно (`KEYS` и `ARGV`).

#### Scenario: Первый вызов скрипта
- **WHEN** скрипт ещё не загружен на сервер (после `SCRIPT FLUSH`), и пользователь вызывает `ScriptEvaluateAsync(script, keys, args)`
- **THEN** клиент получает `NOSCRIPT` на `EVALSHA`, выполняет `EVAL`, и пользователь получает результат скрипта без исключения

#### Scenario: Повторный вызов
- **WHEN** скрипт уже загружен на сервер
- **THEN** выполняется только `EVALSHA`

#### Scenario: Предзагрузка
- **WHEN** вызывается `ScriptLoadAsync(script)`
- **THEN** скрипт загружается через `SCRIPT LOAD`, и возвращённый SHA1 совпадает с предвычисленным

#### Scenario: Ошибка внутри скрипта
- **WHEN** скрипт вызывает `redis.error_reply("boom")`
- **THEN** вызов завершается `RedisServerException` с текстом `boom`

### Requirement: Скрипты только для чтения
`ScriptEvaluateAsync` SHALL поддерживать флаг `readOnly`, при котором используются `EVALSHA_RO`/`EVAL_RO`. Эти команды требуют Redis 7.0+; на более старых серверах вызов MUST завершаться `RedisServerException`, полученной от сервера.

#### Scenario: Скрипт только для чтения на Redis 7
- **WHEN** на Redis 7.x вызывается скрипт с `readOnly: true`, который пытается выполнить `SET`
- **THEN** вызов завершается `RedisServerException`
